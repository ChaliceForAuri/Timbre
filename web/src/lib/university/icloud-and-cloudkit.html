"The app makes zero network requests" is Timbre's headline, and the Library syncs between your devices. Both are true at once. This module is why, and then the part that actually takes design: making two copies of a Library agree.

The claim and the daemon

iCloud on Apple platforms is a system service. Your process writes records into a local container on disk; a system daemon — cloudd — notices, talks to Apple's servers under the user's own account, and writes back what other devices changed. Point nettop or Little Snitch at the Timbre process while sync is on: nothing. The sockets belong to the daemon, and the daemon is the same one that moves Notes and Reminders.

GDR-0010 made this argument first, for the dictionary; GDR-0023 extends it to the whole Library. The distinction is not a trick. "The binary makes no network requests" is a statement about our code, falsifiable with a network monitor, and it stays true. What changes is the headline's second claim, "never leaves your Mac", which becomes "never leaves your devices" the day sync ships, with the sync explained beside it.

The key-value store is what GDR-0010 chose for three lists of strings, and it was right for them. The Library outgrows it twice over: on size, once entries carry meanings, examples and histories; and on merging, because replacing a whole value loses the drill the other device just recorded. CloudKit is the one that lets you say what a conflict means.

CloudKit's shapes

  • Container. An identifier in the app's entitlement; the same container on every target that shares the data.
  • Databases. Public (everyone), private (this user's), shared (records a user shared with others). The Library is private, only.
  • Zones. The private database's custom zones are what sync incrementally: you can ask "what changed since this token" only in a custom zone. The default zone cannot do that, so nothing of ours goes there.
  • Records. A CKRecord has a type, an ID, and fields of simple values; large blobs go in assets. Types and fields are the schema.
  • CKSyncEngine (macOS 14, iOS 17, watchOS 10). You tell it which records are pending; it batches, sends, fetches, retries, keeps the change tokens, and calls you back with what arrived and what conflicted. Before it existed, every app wrote this loop itself, badly.
// The whole conversation, in outline. Core never sees CloudKit; it sees this protocol.
protocol LibrarySync: Sendable {
    func push(_ events: [LibraryEvent]) async throws
    func pull() async throws -> [LibraryEvent]
}

// The CloudKit implementation lives in platform code, behind that door.
final class CloudKitLibrarySync: LibrarySync {
    let engine: CKSyncEngine   // delegate callbacks turn into pushes and pulls
}

Designing for merge

This is the part worth the module. CloudKit will happily do last-writer-wins on a record, and for a number both devices changed that is a coin toss. The Library avoids the question by never syncing a number that could disagree.

  • Events are records, and records are immutable. Each event in an entry's history — taught, met, drilled — is its own record, named by a hash of its content. A device only ever adds records. Two devices that both practised produce two records, not one conflict.
  • Merge is a union. The entry on any device is the union of every event record it has seen, sorted by date. Strength is recomputed from that (Module 12). There is nothing to reconcile because there is nothing that was overwritten.
  • Rare edits take the latest. A meaning, an example, a tag: edited by a person, seldom, on one device at a time. Last edit by timestamp is honest for those, and the field says when it was last changed.
  • Deletions are events too. "Forgot this entry" is a tombstone record, not a deleted record. A deletion that races an addition on another device still lands, and an export can show what was forgotten and when.
// Pure, testable, and the only merge rule the Library has.
func merged(_ a: [LibraryEvent], _ b: [LibraryEvent]) -> [LibraryEvent] {
    Array(Set(a).union(b)).sorted { $0.date < $1.date }
}

Entitlements, environments, and a schema that is forever

Three entitlements: the iCloud container identifiers, icloud-services set to CloudKit, and push notifications if you want to be told about changes rather than polling on launch. A Developer ID app can use iCloud; it needs a provisioning profile embedded in the bundle, which is signing plumbing release.sh already handles (GDR-0010). The App Store builds for iPhone and Watch carry their own.

CloudKit has a development environment, where the schema is created just by saving records, and a production environment, where it is not: you deploy the schema from the CloudKit Console, and from then on you can add record types and fields but never remove or retype one. Every build a user ever ran must still be able to read what a newer build wrote.

Trap · the schema is forever

A field you ship is a field you keep. The event records are designed to be additive for that reason: a new kind of event is a new record type, and an old build that does not know it simply ignores it. Never rename a field; never change its type; never encode a version into a value you may need to query. Put the schema version in the local file and make the file migrate; let the cloud be dumb.

Advanced Data Protection

By default Apple holds the keys to most iCloud data, including third-party apps' CloudKit data, so that account recovery is possible. With Advanced Data Protection turned on by the user, the fields an app stores as CloudKit encrypted values, and its assets, are end-to-end encrypted and Apple cannot read them; plain fields stay under Apple's keys so the server can index them. Timbre's sync writes plain fields today, and the event and entry records' names carry the term, so the Library is encrypted in transit and at rest but not yet end-to-end; GDR-0031 decides the fix before sync ships, and the data inventory tracks it as gap 6. Timbre cannot turn Advanced Data Protection on for anyone. Once GDR-0031's schema lands, the sync setting can say that the Library lives in your iCloud, under your protection setting, and link to Apple's explanation, which is the copy GDR-0010 asked for; until then it says what is true.

Testing without a server

The merge is a unit test: two histories in, one entry out, on every edge you can think of — the same event on both sides, a tombstone racing an addition, a clock that is wrong on one device. None of that touches CloudKit. The sync engine's delegate is tested with a fake LibrarySync that records what was pushed. The only thing that needs the real thing is the real thing: two Macs signed into one Apple ID, a word taught on one, seen on the other, with nettop open beside the Timbre process showing nothing. That is the proof the product map names, and it is the last test, not the first.

In Timbre

TimbreCloud (ADR-0017) is the implementation: CKSyncEngine over one custom zone, three record types — Event named by the event’s id and saved once, Entry replaced whole on edit with the later edited winning, one Profile — and the Library’s own merge doing the merging. A server-changed conflict takes the server’s copy, merges, and sends again over its system fields. The mapping to and from CKRecord is pure and tested offline; the two-device proof is a manual test with nettop open. Sync is off by default, described plainly, and carries the Library and the profile — never a dictation, a capture or a usage count.
