Module 14 said what the other Apple platforms allow. This module is what it took to build on them: Timbre for iPhone and Apple Watch, four targets in one hand-written project, sharing six packages with the Mac (ADR-0016). It is organised by the things that were not obvious, because the obvious parts are in Apple’s templates.

A project file by hand

ADR-0002 rules out project generators, and the Mac project proved a project.pbxproj written by hand with Xcode 16’s synchronized folders is small and stable: each target names a folder, every Swift file in it is compiled, and the file list never drifts. The companion has four targets — the iPhone app, the Watch app, and a WidgetKit extension for each — so the project gains the three things the Mac’s never needed:

  • Embeds. The iPhone app carries its extension in PlugIns (a copy-files phase with dstSubfolderSpec = 13) and the Watch app in Watch (dstSubfolderSpec = 16, dstPath = "$(CONTENTS_FOLDER_PATH)/Watch"). The Watch app embeds its own extension the same way.
  • Dependencies. A target that embeds another must build it first: a PBXTargetDependency with a PBXContainerItemProxy pointing at the other target’s id.
  • Package products per target. Each target lists exactly the products its platform may link (ADR-0015): the iPhone five, the Watch three, each widget one. Xcode resolves the graph from the local package references; nothing is dragged into a workspace.

Everything else is a build setting, and every build setting is in an xcconfig. One exception per target where a key cannot say it: a URL scheme and an extension point are dictionaries, so INFOPLIST_FILE names a plist holding only those, and Xcode merges it with the generated keys.

One container, and a snapshot for the widgets

An app and its extensions are separate processes with separate sandboxes. The one place they can both read is an app group container, named in every target’s entitlements. SharedContainer in TimbreCore is the only code that knows the path, and it falls back to the app’s own Application Support when the entitlement is absent — which is what a simulator build without signing is — so the app still runs.

The temptation is to let the widget open the Library and compute today’s word. Two processes writing one JSON document is a race, and a widget that computes is a widget that can disagree with the app. So the app writes a snapshot — today.json: the term, one line, why, met, and which day — every time its card rebuilds, then asks WidgetKit to reload. The widget reads the snapshot and shows nothing once the day it names has passed. A copy can be a minute behind; it can never be wrong about the day.

App Intents, and a Control that opens a URL

One declaration makes a feature reachable from Siri, Shortcuts, Spotlight and the Action Button. Three were enough: add a word, say a to-do, what is my word of the day. Each uses the app’s one shared coordinator, so a word Siri adds is in the list the screen shows.

Two Swift 6 details cost a build each. An intent’s perform() is called by the system from wherever it likes; with default MainActor isolation on the target, the compiler asks you to say whether the method is on the main actor. Marking it @MainActor is the honest answer — it reads the Library — and the framework hops. And the Control in Control Center runs an intent in the extension’s process, which does not have the app’s model; the built-in OpenURLIntent opens the app on timbre://todo instead, and the app’s onOpenURL picks the tab. No shared intent, no shared process.

Hold to talk

The Mac’s gesture is a held key. On the phone it is a held button: a DragGesture with minimumDistance: 0 starts listening on the first change and stops on end, which also fires when the finger slides off. SpokenInput in TimbreSpeech composes AudioCapture and Transcriber exactly as the Mac’s controller does, minus the overlay and the paste; on iOS it also activates the audio session, which the Mac never needed. Live text streams while the finger is down; the release returns the finished transcript; Spell it reads the letters from it.

The wrist: text input, and a lesson

watchOS has no SpeechAnalyzer (Module 14), so speech input is the system’s own: TextFieldLink opens the dictation sheet and hands back a String. That is enough for the to-do key, for Spell it and for banking a word you heard, and it needs no permission of ours.

Then the first build against the SDK stopped on saveReminder. EventKit is in the watchOS SDK; its writes are __WATCHOS_PROHIBITED. GDR-0026 had promised a Watch that files its own to-dos, on the strength of a framework folder existing. GDR-0029 is the correction: the wrist parses and queues, the iPhone files. The queue and the message shape live in TimbreRelay — WatchConnectivity is a framework, so it is a package (ADR-0015) — and transferUserInfo carries each to-do when the phone is reachable, launching the iPhone app in the background to receive it. A to-do said in a tunnel is late, not lost.

Trap · crossing actors with a dictionary

WatchConnectivity delivers [String: Any] on its own queue. Hand that to a Task { @MainActor in … } and Swift 6 refuses: Any is not Sendable, and the compiler cannot prove nobody else holds the dictionary. Parse it before crossing — a UUID and a Todo are Sendable — and pass those. The rule generalises: the boundary between a framework’s callback queue and your actor is where to turn loose data into typed values, not after.

In Timbre

One project, four targets, settings in xcconfig; each target links only what its platform allows. The app and its widgets share a container through SharedContainer; the widgets read today.json, never the Library. Three App Intents share one coordinator; the Control opens a URL. Hold to talk is a drag gesture over SpokenInput. The Watch takes text from the system’s dictation, reads the Reminders list, and hands new to-dos to the phone through TimbreRelay. GDR-0029 records the mistake that taught the last part.
